# K003 — Must-rule without examples

**Severity:** info
**Category:** Completeness

## What this catches

A rule with `severity = "must"` and **both** `example_good` and
`example_bad` empty or missing.

Example that fires:

```toml
[[rules]]
id = "STYLE-001"
title = "Use type hints on every public function"
severity = "must"
rationale = "Static analysis catches more issues before runtime."
# missing: example_good and example_bad
```

## Why it matters

Examples cement understanding more reliably than prose for the LLM.
Two engineers can read the same rule and disagree about edge cases —
a single `example_good` collapses that disagreement.

The rule is INFO (not WARNING) because examples are recommended but
not required. A short, well-named rule may be self-explanatory; a
nuanced one almost always benefits from one example each way.

## Suggested fix

Add at least one of `example_good` or `example_bad`:

```toml
[[rules]]
id = "STYLE-001"
title = "Use type hints on every public function"
severity = "must"
rationale = "Static analysis catches more issues before runtime."
example_good = """
def parse_ctx_file(path: Path) -> Document: ...
"""
example_bad = """
def parse_ctx_file(path): ...
"""
```

Either field alone satisfies K003 — the analyzer is happy with one example.

## When to silence

For very short rules where the title itself is the example
(`Use 4 spaces, no tabs`), examples are redundant. Silencing K003 is
reasonable here.
