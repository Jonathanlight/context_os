# R006 — Large source without `header_aware` chunking override

**Severity:** info
**Category:** RAG / chunking sanity

## What this catches

A `[[document]]` entry whose `max_size_kb` is **≥ 500 KB** and which
doesn't override `chunking_strategy` to `"header_aware"`.

## Why it matters

A 500 KB document spans hundreds of paragraphs. Under fixed or
semantic chunking, the chunker produces a long sequence of chunks
without a clean anchor structure, and:

- **Retrieval surfaces fragmented chunks** — the LLM sees a slice of
  text without the section heading that gave it context.
- **The reranker has poor signal** — adjacent chunks are similar
  enough that ordering becomes noisy.
- **Embedding cost balloons** without a recall payoff — you embed
  hundreds of near-duplicate chunks instead of dozens of clean ones.

Header-aware chunking on a long document keeps the headings as
chunk anchors, so retrieval brings back "section 4.2 of the
deployment runbook" rather than "paragraph 137 of an unnamed file."

## Suggested fix

Set the override on the long entry:

```toml
[[document]]
source = "docs/runbooks/full-deployment-guide.md"
max_size_kb = 800
chunking_override = "header_aware"
required_anchors = ["##"]
```

If the document genuinely lacks heading structure (a 500 KB text
file of free-form notes), the better fix is upstream: **split the
source into smaller files** that each have a meaningful identity.

## When to silence

R006 is INFO. Long files with stable, predictable structure (e.g.,
generated API references with one section per endpoint) can chunk
fine under semantic strategies — the rule is a heuristic, not a
defect.
