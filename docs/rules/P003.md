# P003 — Bare URL in title

**Severity:** warning
**Category:** Platform

## What this catches

A rule title containing a literal `http://` or `https://` URL.

Examples that fire:

- `Read the deploy runbook at https://example.com/runbooks/deploy`
- `OAuth tokens documented at https://docs.example.com/oauth`
- `Reject requests to http://internal.example.com/admin`

## Why it matters

A URL in a rule title clutters the directive with metadata that
belongs in a structured field. The rule still has to say what to do
*about* the URL; the URL itself is supporting evidence, not the
directive.

Two practical consequences:

- Many emitters render URLs as bare text in the target file. If the
  target supports Markdown links (`CLAUDE.md` does), the structured
  `links` field gives the consumer a proper hyperlink instead of a
  string.
- URLs in titles tokenize unpredictably — a long path inflates the
  rule's token cost without adding directive signal.

## Suggested fix

Move the URL to the rule's `links` field; keep the title focused on
the behaviour:

```toml
# Before (P003 fires):
[[rules]]
title = "Read the deploy runbook at https://example.com/runbooks/deploy before any prod change"

# After:
[[rules]]
title = "Read the deploy runbook before any prod change"
links = ["https://example.com/runbooks/deploy"]
```

For rules that *reject* a URL (a blocklist directive), describe the
pattern rather than the literal URL:

```toml
title = "Reject requests to the internal admin endpoint"
example_bad = "http://internal.example.com/admin"
```

## When to silence

If the URL is genuinely the operational atom of the rule — a
deprecated endpoint that must be blocked, say — and you've already
moved supporting metadata to `links`, leaving the URL in the title is
acceptable. Silence P003 explicitly and document why.
