# A004 — Hedging cadence

**Severity:** warning
**Category:** Ambiguity

## What this catches

A rule that prescribes a recurring action without naming the trigger.
Cousin to A003 (vague quantifier) — A003 hedges the *scope*, A004 hedges
the *frequency or condition*.

Examples that fire:

- `Refresh credentials regularly`
- `Add tests as needed`
- `Validate inputs if necessary`
- `Refactor when appropriate`
- `Pin dependencies if possible`

## Trigger phrases

`regularly`, `as needed`, `when appropriate`, `if necessary`, `if possible`,
`from time to time`, `every now and then`, `when in doubt`,
`where it makes sense`, `where appropriate`.

Match is on whole-token boundaries, case-insensitive. Multi-token phrases
must appear as a contiguous span.

## Why it matters

The LLM cannot operationalize "regularly" without a calendar, a workload
signal, or a coverage metric to anchor it to. The rule reads as a
directive but never fires; tokens spent without behavioural effect.

## Suggested fix

Tie the cadence to a measurable trigger or eliminate the rule:

| Hedging | Concrete |
|---|---|
| Refresh credentials regularly | Rotate credentials on every deployment |
| Add tests as needed | Every public function has a test; every bug fix has a regression test |
| Validate inputs if necessary | Validate every input crossing a trust boundary (HTTP handler, CLI parser, FS read) |
| Refactor when appropriate | Refactor when a function exceeds 40 lines or 5 levels of nesting |
| Pin dependencies if possible | Pin every direct dependency in `pyproject.toml`; lock transitive deps via `uv lock` |

## When to silence

If the cadence really is human judgment (e.g. project-management text
mixed into the rules), move that text to prose. Rules are for the model.
