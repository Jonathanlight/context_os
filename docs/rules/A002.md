# A002 — Subjective adjective

**Severity:** warning
**Category:** Ambiguity

## What this catches

A rule title that uses an adjective whose meaning is in the eye of the
beholder. Two engineers reading the same word disagree about what it
demands; the LLM disagrees with both.

Examples that fire:

- `Write clean code`
- `Use a proper variable name`
- `Pick a reasonable timeout`
- `Avoid ugly hacks`
- `Keep the API nice`

## Trigger words

`clean`, `good`, `bad`, `nice`, `elegant`, `proper`, `appropriate`,
`suitable`, `reasonable`, `sensible`, `smart`, `stupid`, `ugly`,
`beautiful`, `tidy`, `messy`.

Match is whole-token, case-insensitive: `cleanly` does not fire, `clean`
does. Multiple offenders in the same rule produce a single diagnostic
listing them all.

## Why it matters

Subjective adjectives feel like guidance but carry no operational meaning.
The LLM falls back to its training distribution, which varies model to
model and even prompt to prompt. The rule looks enforced but isn't.

## Suggested fix

Replace the subjective term with the concrete criterion it stood in for:

| Subjective | Concrete |
|---|---|
| Clean | "no function > 5 levels of nesting", "no global mutable state" |
| Proper naming | "snake_case for functions, PascalCase for classes" |
| Reasonable timeout | "5 seconds for synchronous requests, 60 for batch" |
| Nice API | "every public function has a docstring and a type-annotated signature" |
| Elegant solution | (drop the rule — elegance is not enforceable) |

## When to silence

If the rule's narrative deliberately uses the word for human readers
(rare in a rules section), move it to a free-form prose block instead of
`[[rules]]`. Rules are for things the LLM should check; prose is for
things it should know.
