# S003 — Description is approaching the hard cap

**Severity:** info
**Category:** Skill / description quality

## What this catches

A `SKILL.md` whose `description` exceeds the **800-character soft cap**.
The hard cap enforced by the AST (`DESCRIPTION_MAX_CHARS`) is 1024 —
S003 surfaces before that wall to give you breathing room.

## Why it matters

The description is loaded into the model's context **every time the
skill is registered**, even when the user prompt is unrelated to the
skill. A 900-character description in a registry of 20 skills costs
~18 KB of context, every prompt. That budget comes out of the user's
input window.

The trigger signal does not get sharper past ~400 characters — past
that, you are paying tokens to repeat yourself or to describe what
the body should describe.

## Suggested fix

Move the long-form material out of the description and into the body:

```yaml
# Before — 900-char description doing the body's job
description: |
  Extracts structured data from PDF invoices. Supports French and
  English invoices. Returns JSON with vendor name, total amount,
  tax breakdown, line items, currency code, and payment terms.
  Optional fields include due date, PO number, ... [continues for
  600 more characters listing every feature, edge case, and known
  limitation of the extractor pipeline]
```

```yaml
# After — description names the trigger, body covers the rest
description: |
  Extracts structured invoice data from PDF documents. Triggers when
  the user uploads a `.pdf` invoice or asks to parse one.
```

```markdown
# Body of SKILL.md

## Supported fields

- vendor name, total amount, tax breakdown, line items, ...

## Languages supported

- French, English (others ignored)
```

## When to silence

If the skill genuinely needs a long trigger signal — for example, it
encodes a complex multi-condition routing rule that the model
otherwise mis-routes — S003 is INFO so it won't break CI. Tune your
ramp once you have evidence the longer signal materially improves
routing.
