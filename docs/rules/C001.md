# C001 — Contradiction (antonym overlap)

**Severity:** warning
**Category:** Contradiction

## What this catches

Two rules where:

1. One rule's title contains a word from a known antonym pair
   (e.g. `always`, `required`, `public`, ...).
2. The other rule's title contains the *opposite* of that word
   (`never`, `forbidden`, `private`, ...).
3. The two rules share at least one substantive token after removing
   stopwords and the antonym words themselves.

Examples that fire:

```toml
[[rules]]
id = "STYLE-001"
title = "Always use type hints on public functions"
severity = "must"

[[rules]]
id = "STYLE-014"
title = "Never use type hints in benchmark scripts"
severity = "should"
```

Both rules talk about `type hints`. One says *always*, the other says
*never*. Without an `applies_to` scope to keep them disjoint, the LLM
sees conflicting guidance.

Examples that **do not** fire:

```toml
[[rules]]
title = "Always validate inputs"

[[rules]]
title = "Never panic"
```

Antonym pair present (`always` / `never`) but no shared subject — the
heuristic correctly stays silent.

## Antonym pairs

`always/never`, `required/forbidden`, `allowed/prohibited`,
`allow/forbid`, `enable/disable`, `include/exclude`, `public/private`,
`mutable/immutable`, `synchronous/asynchronous`, `sync/async`,
`encrypted/plaintext`, `local/remote`, `explicit/implicit`,
`before/after`.

Multi-word antonyms (`must not`, `should not`) are out of scope for
the lexical pass. NLI-based detection will catch those.

## Why it matters

Contradictions confuse the model and the human reviewer. The LLM has
no policy to resolve them; it picks one — often the most recent — and
the choice is invisible to the author. Bugs hide here.

## Suggested fix

Two options:

1. **Pick one** — decide which directive is correct for the shared
   subject, and delete or rewrite the other.

2. **Scope them** — if both rules really apply, give each an
   `applies_to` that doesn't overlap:

   ```toml
   [[rules]]
   id = "STYLE-001"
   title = "Always use type hints on public functions"
   applies_to = ["src"]

   [[rules]]
   id = "STYLE-014"
   title = "Never use type hints in benchmark scripts"
   applies_to = ["bench"]
   ```

   With disjoint scopes, the contradiction dissolves. (A future
   analyzer pass will treat `applies_to` as a precondition and skip
   C001 when the scopes don't overlap; today the heuristic doesn't
   check this and may still fire — silence it manually if so.)

## Precision and recall

Internal estimate (`.claude/ALGORITHMS.md` §6): ~80 % precision,
~50 % recall on the lexical heuristic alone. Most missed cases use
multi-word antonyms or rely on world knowledge (`HTTPS` vs `HTTP`
without explicit `secure` / `insecure` markers).

NLI-based detection (post-MVP) will widen recall to ~90 %+ at the cost
of an ML dependency and per-pair latency.

## When to silence

If the rules are genuinely scoped to disjoint contexts and the
analyzer fires anyway, that's a false positive — the heuristic doesn't
yet read `applies_to`. The fix is either to wait for the cross-rule
scope check (Phase 3+) or to combine the rules into one with a clearer
title.
