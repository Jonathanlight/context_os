# P001 — Personal absolute path

**Severity:** warning
**Category:** Platform

## What this catches

A rule title that contains a user's home directory baked into the
text. The detector recognizes three shapes:

- macOS: `/Users/alice/...`
- Linux: `/home/alice/...`
- Windows: `C:\Users\alice\...`

Examples that fire:

- `Store credentials in /Users/jonathan/.config/myapp/secrets.json`
- `Run /home/alice/bin/check.sh before every PR`
- `Logs land in C:\Users\bob\AppData\Roaming\MyApp\logs`

## Why it matters

A rule that names an absolute path with someone's username works on
exactly one machine. When the file ships to a repo, every other
developer reads a directive they can't follow. The LLM, parsing the
literal path, may try to operate on a directory that doesn't exist.

Beyond the practical problem, the username leaks personal information
into a shared artifact. Most CI workflows redact `/Users/<name>` from
logs for this reason.

## Suggested fix

Replace the absolute path with a project-relative path or a
documented placeholder. Move the location detail to `rationale` or
`links` if context matters:

```toml
# Before (P001 fires):
[[rules]]
title = "Store credentials in /Users/jonathan/.config/myapp/secrets.json"

# After:
[[rules]]
title = "Store credentials under ~/.config/myapp/"
rationale = "XDG-compliant location; readable by the app at startup."
```

The tilde (`~`) is a portable shell shorthand and the analyzer does
not flag it.

## When to silence

If the rule deliberately describes a remote machine you control (a
production-only directive, say) and the username is intentional,
suppress P001 manually. This is rare.
