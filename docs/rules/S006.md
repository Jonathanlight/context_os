# S006 — `trigger_keywords` already present in the description

**Severity:** info
**Category:** Skill / body coherence

## What this catches

Every entry in `trigger_keywords` appears verbatim (case-insensitive)
in the `description` text. The `trigger_keywords` field adds zero
signal beyond what the description already carries.

If even one keyword is *not* already in the description, the rule
stays silent — the keyword list is doing genuine work in that case.

## Why it matters

`trigger_keywords` is meant to add lexical hints the description does
not already cover. Synonyms, foreign-language spellings, abbreviations,
common typos — the keyword list catches the cases where the user's
phrasing doesn't match the description's phrasing.

When every keyword is already in the description, the list is just
spending bytes restating what the model already saw. The model would
fire on those tokens through the description alone.

## Suggested fix

Either remove the field:

```yaml
# Before
description: |
  Extracts PDF invoices. Triggers when the user uploads an invoice PDF.
trigger_keywords:
  - pdf
  - invoice
```

```yaml
# After — keyword field removed (description already covers it)
description: |
  Extracts PDF invoices. Triggers when the user uploads an invoice PDF.
```

Or extend it with terms the description doesn't cover:

```yaml
description: |
  Extracts PDF invoices. Triggers when the user uploads an invoice PDF.
trigger_keywords:
  - pdf
  - invoice
  - facture   # French
  - bill      # synonym
  - receipt   # related artifact
```

## When to silence

The current heuristic is purely lexical. A future revision may use
synonyms or embeddings to detect cases where a keyword is
*semantically* present but lexically absent — e.g. `description`
mentions "invoice" and `trigger_keywords` includes "bill". Until then,
S006 misses those cases and may also fire on legitimate keyword lists
where the author values explicit redundancy.
