# R002 — Tight headroom between `chunk_target` and `chunk_max`

**Severity:** info
**Category:** RAG / chunking sanity

## What this catches

`chunk_max_tokens` sits less than **20%** above `chunk_target_tokens`.
The default in SPEC §1.4.1 has target 500 / max 1500 — 200% headroom,
plenty of slack.

## Why it matters

Header-aware and semantic chunkers regularly produce chunks larger
than the target when:

- A heading section is naturally longer than the target (a long ADR
  with no sub-headings).
- A semantic boundary lands past the target token count and splitting
  it would break the thought.

Without headroom, the chunker hits the ceiling and either truncates
the chunk (losing the tail of the section) or falls back to fixed
chunking (losing the semantic anchor that was the whole point). Both
hurt retrieval quality on the long tail of large sections.

## Suggested fix

Raise `chunk_max_tokens` so the chunker has room to bend:

```toml
[rag]
chunk_target_tokens = 500
chunk_max_tokens = 1500   # 200% headroom, default
```

For corpora with very uniform section sizes (e.g., generated
documentation with one paragraph per section), tight headroom is
acceptable. For mixed-source corpora it's a footgun.

## When to silence

R002 is INFO so it never breaks CI. If you've measured retrieval
quality on your corpus and tight headroom is fine, the rule is just
noise — set it aside.
