# X002 — Unfilled template placeholder

**Severity:** warning
**Category:** Anti-pattern

## What this catches

A rule title containing a placeholder shape the analyzer recognizes as
"copied from a template and never customized":

| Pattern | Example |
|---|---|
| `<UPPER_SNAKE>` | `Use <DB_DRIVER> for all queries` |
| `{lower_word}` | `Configure {your_project_name} via env vars` |
| `[INSERT ...]` | `Run [INSERT TEST COMMAND] before each PR` |

Match is on the raw text; no rendering needed. The first placeholder
found is named in the diagnostic message.

## Why it matters

Every starter template ships with placeholders the user is expected to
replace. When the placeholder survives into a shipped `.ctx`, the LLM
sees either a literal `<DB_DRIVER>` token (meaningless) or a directive
that mentions an undefined project (meaningless plus confusing if the
project name doesn't match the file).

## Suggested fix

Replace the placeholder with the actual value, or delete the rule if
the template's assumption no longer applies:

```toml
# Before — template never customized:
[[rules]]
id = "DB-001"
title = "Use <DB_DRIVER> for all queries"
severity = "must"

# After:
[[rules]]
id = "DB-001"
title = "Use asyncpg for all queries against the primary database"
severity = "must"
```

## Tuning

The regex is `<[A-Z_][A-Z0-9_]*>|\{[a-zA-Z_][a-zA-Z0-9_\-]*\}|\[INSERT[^\]]*\]`.
Three shapes only, chosen to minimize false positives:

- `<...>` requires UPPER_SNAKE_CASE — avoids matching legitimate HTML/JSX in a code block.
- `{...}` requires a simple identifier — avoids matching JSON literals or Python f-string expressions in titles (rare, but they exist).
- `[INSERT ...]` requires the literal word `INSERT` — avoids matching Markdown link references.

If a real placeholder shape escapes these patterns, file an issue and
we'll widen the regex with a regression test.
