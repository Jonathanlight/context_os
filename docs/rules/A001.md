# A001 — Vague directive

**Severity:** warning
**Category:** Ambiguity

## What this catches

A rule whose title is a generic instruction the LLM cannot operationalize
because it carries no measurable criterion.

Examples that fire:

- `Be concise`
- `Write clean code`
- `Use good naming`
- `Be careful`
- `Avoid bad practices`
- `Follow best practices`

The match is normalized (lowercase, trailing punctuation stripped) and
prefix-matched, so `Be concise about error messages` also fires.

## Why it matters

A directive without a measurable definition leaves every concrete decision
to the model's defaults. Two engineers reading "be concise" will disagree
about line counts; the LLM will too. The rule reads as guidance but cannot
be enforced by the analyzer or the model, so it adds tokens without
shaping behaviour.

## Suggested fix

Rephrase with a concrete, measurable criterion that an analyzer or a code
review can check:

| Vague | Concrete |
|---|---|
| Be concise | Public functions ≤ 40 lines |
| Use good naming | `snake_case` for functions, `PascalCase` for classes |
| Write clean code | No global mutable state; no function > 5 levels of nesting |
| Be careful with errors | Every public function declares its exception contract in the docstring |
| Avoid bad practices | List the specific anti-patterns in a `## Forbidden patterns` section |

## When to silence

If the rule is intentional placeholder text for a future iteration, move
it to a `[[notes]]` block or drop it. Vague rules left in the file degrade
the signal of the rules around them.
